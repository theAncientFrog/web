# Стратегія i18n для UI + Динамічні дані з БД

## 📊 Порівняння стратегій зберігання перекладів

### Варіант 1: Окремі колонки (name, nameEn, description, descriptionEn)
**Плюси:**
- ✅ Прості запити (SELECT name, nameEn FROM dishes)
- ✅ Швидка індексація (BTree індекси)
- ✅ Легко додавати нові мови (nameFr, nameDe)
- ✅ Нульові JOIN'и - найшвидші запити
- ✅ Простий пошук (WHERE name ILIKE '%query%' OR nameEn ILIKE '%query%')

**Мінуси:**
- ❌ Збільшення кількості колонок при додаванні мов (3 мови = 6 колонок)
- ❌ Складніше міграції при зміні структури
- ❌ Дублювання логіки вибору мови в кожному запиті

**Висновок:** ✅ **РЕКОМЕНДОВАНО** для 2-3 мов (en, ua, можливо ru)

---

### Варіант 2: JSONB колонка (translations JSONB)
**Плюси:**
- ✅ Гнучкість - легко додавати нові мови без міграцій
- ✅ Компактність - одна колонка для всіх мов
- ✅ Можливість зберігати метадані (author, updated_at для перекладу)

**Мінуси:**
- ❌ Складніші запити (translations->>'en', translations->>'ua')
- ❌ Потрібні GIN індекси для пошуку (більше пам'яті)
- ❌ Складніше валідація на рівні БД
- ❌ Менш зрозумілі запити для розробників

**Висновок:** ⚠️ Підходить для 4+ мов або динамічних мов

---

### Варіант 3: Окрема таблиця Translations
**Плюси:**
- ✅ Нормалізація - один запис на мову
- ✅ Легко додавати нові мови без зміни схем
- ✅ Можна додавати метадані (translator, verified, etc.)

**Мінуси:**
- ❌ Обов'язкові JOIN'и в кожному запиті
- ❌ Складніші запити (LEFT JOIN translations ON ...)
- ❌ Потенційно повільніше для простих запитів
- ❌ Більше коду для обробки

**Висновок:** ⚠️ Підходить для великих проектів з багатьма мовами (5+)

---

## 🎯 Рекомендація для цього проекту

**Вибір: Варіант 1 (Окремі колонки)**

**Аргументація:**
1. **Продуктивність:** 2 мови (ua, en) - найшвидші запити без JOIN'ів
2. **Розширюваність:** Легко додати 3-ю мову (ru) через міграцію
3. **Індексація:** BTree індекси працюють ідеально для окремих колонок
4. **Складність запитів:** Мінімальна - просто SELECT nameEn або name
5. **Пошук:** Простий ILIKE по обох колонках

**Коли переходити на JSONB:**
- Якщо потрібно 4+ мов
- Якщо мови додаються динамічно (через адмін-панель)
- Якщо потрібні метадані перекладів

## 📐 Структура даних

### Поточна структура (вже існує):
```prisma
model Category {
  name         String
  nameEn       String?
  description  String?
  descriptionEn String?
}

model Dish {
  name        String
  nameEn      String?
  description String?
  descriptionEn String?
}
```

### Рекомендована структура (з fallback):
- `name` - завжди українська (fallback)
- `nameEn` - англійська (опціональна)
- Якщо `nameEn` NULL → використовуємо `name`

---

## 🔄 Fallback стратегія

1. **Backend:** Якщо `nameEn` NULL → повертаємо `name`
2. **Frontend:** Якщо API повернув NULL → використовуємо fallback
3. **UI:** Завжди показуємо щось (ніколи не показуємо NULL)

---

## 📈 Індексація для пошуку

```sql
-- Індекси для швидкого пошуку
CREATE INDEX idx_dish_name_gin ON dish USING gin(to_tsvector('ukrainian', name));
CREATE INDEX idx_dish_name_en_gin ON dish USING gin(to_tsvector('english', name_en));

-- Або простіші BTree індекси для ILIKE
CREATE INDEX idx_dish_name_trgm ON dish USING gin(name gin_trgm_ops);
CREATE INDEX idx_dish_name_en_trgm ON dish USING gin(name_en gin_trgm_ops);
```
